# Replacing the original project module

The standalone package derives from `FourByFourAT_CategoryRanking` and uses a new namespace, configuration paths, snapshot table, indexer ID and search-field prefix. It does not migrate or modify the original project's files automatically.

Do not enable both ranking modules together: both add a category default and intercept category search sorting. Plan this change in the project's deployment pipeline and take the normal database backup first.

1. Record the original `fourbyfourat_category_ranking/general/enabled` values at default, website and store scope, plus the global excluded order entity IDs.
2. Install the Composer package in the Magento project. Enter maintenance mode for the switch, disable `FourByFourAT_CategoryRanking`, enable `Willwright_CategorySorting`, and run `php bin/magento setup:upgrade --safe-mode=1` followed by the normal DI compilation steps. Disabling the original module allows this upgrade to drop its whitelisted snapshot table, even while its code remains present. Safe mode saves affected data for destructive schema changes; retain the project's normal full database backup as well.
3. Copy the recorded values to `willwright_category_sorting/general/enabled` at the same scopes and the global excluded IDs to `willwright_category_sorting/general/excluded_order_ids`. Review the optional `use_amasty_preorder` setting. Clean configuration cache before building.
4. Rebuild stock, the optional Amasty preorder index, `willwright_category_sorting`, then `catalogsearch_fulltext`. The new table is rebuilt from source data; the old snapshot and refresh flag do not need copying.
5. Update any theme checks for `fourbyfourat_recommended` to `willwright_recommended`. The 4x4AT theme's sorter template currently checks the old code when hiding the direction arrow. Rebuild static content and clear application/external page caches using the normal deployment procedure.
6. Verify an unfiltered and filtered category, consecutive pages, configurable availability, preorders, and manual price sorting. Repeat as customers from different price groups. Leave maintenance mode after verification.

There is no `replace` declaration pretending that the two module names are equivalent. The old project's module code can be removed in a subsequent reviewed change after it is disabled everywhere. **Keeping the disabled module's schema file does not preserve its table**: Magento stops reading that schema while still reading its whitelist, so `setup:upgrade` can drop the old snapshot during the initial switch. Its snapshot is disposable and can be rebuilt from orders, ratings and inventory, but confirm the schema operations in staging first. See [Adobe's guidance on disabling declarative-schema modules](https://developer.adobe.com/commerce/php/development/components/declarative-schema/configuration#disable-a-module).

For rollback, remain in maintenance mode, disable the new module, re-enable the original, run `setup:upgrade --safe-mode=1` to recreate any dropped original snapshot table, and compile DI. Rebuild the original ranking and full catalog-search indexes, restore the original theme sort-code checks, and clean application/external caches before leaving maintenance mode. The new module's snapshot can also be dropped during this reverse switch. Retain the recorded settings until the migration is verified.
